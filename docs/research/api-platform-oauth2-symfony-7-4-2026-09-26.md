Research for [Research API Platform and OAuth2 integration options for Symfony 7.4](https://github.com/lbacik/paysubscriptions/issues/85), checked 2026-09-26. This is evidence for a planning decision, not a product-policy choice or an installation test.

## Option A: authorization server in the Symfony application

The League bundle supplies `/authorize`, `/token`, `/device-code`, Doctrine persistence for clients and tokens, and a Symfony `oauth2` firewall for bearer-token validation. It documents a separate stateless `/api` firewall and access control requiring an already signed-in user at `/authorize`; this lets the existing web login remain the approval login. The application must manage signing/encryption keys, client registration, token tables/migrations, cleanup jobs, grant configuration, consent experience, key rotation and incidents. [Bundle setup](https://github.com/thephpleague/oauth2-server-bundle/blob/1.x/docs/basic-setup.md), [configuration](https://github.com/thephpleague/oauth2-server-bundle/blob/1.x/docs/index.md), [routes](https://github.com/thephpleague/oauth2-server-bundle/blob/1.x/config/routes.php).

The bundle's client command supports public clients, redirect URIs, allowed grants/scopes and a `plain` PKCE opt-in. The League server requires a code challenge for public clients by default. Use authorization code with S256 PKCE for public clients; RFC 9700 also requires code-injection defenses for confidential clients and recommends PKCE. Browser/native client policy remains to be decided by the user. [Bundle client administration](https://github.com/thephpleague/oauth2-server-bundle/blob/1.x/docs/basic-setup.md), [League PKCE upgrade note](https://oauth2.thephpleague.com/upgrade-guide/), [OAuth Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html).

Scopes are configured as available/default values and can be restricted per route or checked through generated `ROLE_OAUTH2_<scope>` roles. The docs warn that a client with no scope may effectively access all scopes; define a narrow default and test both route/operation scope checks and user ownership. API Platform's Symfony security expressions can enforce object access; custom state providers/processors can protect collection reads and route writes through existing services. [Bundle scope guide](https://github.com/thephpleague/oauth2-server-bundle/blob/1.x/docs/token-scopes.md), [bundle firewall and roles](https://github.com/thephpleague/oauth2-server-bundle/blob/1.x/docs/basic-setup.md), [API Platform security](https://api-platform.com/docs/v4.2/symfony/security/), [state processors](https://api-platform.com/docs/v4.2/core/state-processors/).

The bundle's published route file has authorize, token and device-code routes, but no RFC 7009 revocation endpoint. It has token persistence and expiry cleanup, but client-facing revocation and user token administration require design/implementation or another component. A revoked JWT is only rejected immediately if the resource server checks revocation state; purely offline signature validation leaves the token usable until expiry. This is an architectural inference from the route file, the bundle's local persistence, and the introspection/revocation standards, and must be tested with the chosen firewall. [Bundle routes](https://github.com/thephpleague/oauth2-server-bundle/blob/1.x/config/routes.php), [RFC 7009](https://www.rfc-editor.org/rfc/rfc7009.html), [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html).

## Option B: external authorization server, Symfony as resource server

An external server handles client registration, authorization, token issuance, keys and revocation; Symfony retains user data and API authorization. Keycloak is an illustrative self-hosted external boundary, not a recommendation: its official docs expose authorization/token, JWKS, introspection and revocation endpoints and client-level S256 PKCE enforcement. A managed provider can occupy the same protocol boundary, subject to its contract. [Keycloak OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers), [Keycloak client configuration](https://www.keycloak.org/docs/latest/server_admin/).

Symfony's access-token firewall reads `Authorization: Bearer` by default. Its OIDC token handler can validate JWT signatures, issuer and audience with a keyset/discovery; `OidcUserInfoTokenHandler` fetches user info remotely. A custom token handler can call RFC 7662 introspection when active/revoked state is required per request. Map the external subject (`iss`,`sub`) to the existing local User and verify the token is intended for this API (`aud`), then apply scopes and owner checks. Do not use an ID token as the API access token. [Symfony access-token authentication](https://symfony.com/doc/current/security/access_token.html), [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html), [RFC 8414](https://www.rfc-editor.org/rfc/rfc8414.html).

Offline JWT verification avoids a network hop per request but needs key/discovery caching and leaves an access token valid until expiry unless extra revocation checks are added. Introspection gives current active state, at the cost of provider availability, latency, client credentials and cache/timeout policy. These are operational inferences from the [Symfony token-handler options](https://symfony.com/doc/current/security/access_token.html) and [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html). An external boundary also introduces user identity linking/migration and issuer/audience/key-rotation configuration; hosted service terms and cost need separate evaluation.

## Cross-cutting constraints for the plan

1. Select client types and grant policy before choosing the authorization-server boundary. For human users, authorization code with PKCE is the standard path; client credentials represents a client rather than the app User and cannot automatically authorize user-owned records. Avoid password and implicit grants per RFC 9700. [League grant guidance](https://oauth2.thephpleague.com/authorization-server/which-grant/), [OAuth Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html).
2. Define scopes as coarse client permissions and enforce local User ownership independently on every item, collection, mutation and report. Scope claims do not identify the record owner. [API Platform security](https://api-platform.com/docs/v4.2/symfony/security/), [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749.html).
3. Specify revocation target (refresh only, access too), acceptable access-token survival time, and validation mode. RFC 7009 defines the revocation request; RFC 7662 reports whether a token is active. [RFC 7009](https://www.rfc-editor.org/rfc/rfc7009.html), [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html).
4. Keep session-based web firewall separate from stateless bearer API firewall. API Platform documents OAuth in generated OpenAPI/Swagger UI, but this advertises a scheme and does not implement an authorization server. [Bundle firewall setup](https://github.com/thephpleague/oauth2-server-bundle/blob/1.x/docs/basic-setup.md), [API Platform OpenAPI OAuth configuration](https://api-platform.com/docs/v4.2/core/openapi/).

No dependencies were installed or Composer solver run during this research. Package metadata establishes declared constraints; it is not a compatibility test of this application's full lockfile and runtime configuration.
