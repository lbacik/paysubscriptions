# Self-hosted Elasticsearch for production error logging, not a third-party error-tracking SaaS

As part of defining the v1.0 release-quality bar ([issue #24](https://github.com/lbacik/paysubscriptions/issues/24)), we needed a way for a solo maintainer to see production errors like the `/register`, `/contact`, and `/reset-password` HTTP 500s found in the baseline ([issue #20](https://github.com/lbacik/paysubscriptions/issues/20)). We considered a third-party error-tracking SaaS (e.g. Sentry) against structured logging into a self-hosted Elasticsearch instance, and chose self-hosted ES: it avoids introducing a new third-party sub-processor that would need disclosure alongside Umami under the v1.0 privacy commitments ([issue #30](https://github.com/lbacik/paysubscriptions/issues/30)), keeping "no selling / no third-party sharing" intact without extra policy work. Proactive alerting on top of these logs (e.g. a Kibana alert on error-rate spikes) is deliberately out of scope for v1.0 and deferred to a follow-up issue; v1.0 only requires that exceptions are captured as structured logs.
